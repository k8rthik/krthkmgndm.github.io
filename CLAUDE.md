# keerthik.dev

Personal site: Next.js (App Router, JS not TS), deployed on Vercel.
Plain-HTML aesthetic — browser defaults, Times + Courier New, almost no
styling. That restraint is the design; protect it.

## Commands

- `npm run dev` — dev server (turbopack)
- `npm test` — node:test suite (`tests/*.test.js`), zero test dependencies
- `npm run build` — production build; CI runs test + build on every push
- `npm run helix` — regenerate `lib/helixFrames.js` (never hand-edit it)

## Architecture

- `app/` routes · `components/` UI · `lib/` loaders and pure helpers ·
  `data/` generated payloads (never hand-edit)
- `content/` is everything edited by hand: `site.js` (identity, links,
  homepage counts), `projects.json`, `posts/*.md`. Page- and post-specific
  values stay with their page.
- Shared across dashboards: `components/chart/scale.js` (scales, paths,
  pointer mapping, label spacing, ticks) and `lib/format.js` (num, signed,
  usd, pct). Don't re-implement either inside a chart.
- Styles: `app/globals.css` is an ordered `@import` index over
  `app/styles/*.css`, one file per feature; colors and fonts live only in
  `app/styles/tokens.css`.
- `/bgelo` dashboard: `data/elo.json` is generated by the bgelo repo and
  synced via `python3 -m bgelo.site_sync` — **never hand-edit it**. The
  export contract is enforced by `tests/data-invariants.test.js`.
- Dashboard split: `components/elo/asOf.js` + `insights.js` are pure
  derivations (raw-Node loadable, fully tested); components are dumb
  renderers. New logic goes in the derivation layer, not in JSX.

## Writing descriptions

Applies to `content/projects.json` and post frontmatter `description`.

- **One sentence, ending in a period.** It says what the thing *is*,
  not how it was built.
- **Projects: concise, technical, impressive.** Lead with the tech
  (*"RDKit random forest and GNN model that predicts…"*), then what it
  does, then at most one number, and only if it impresses on its own
  (*"over 55,000 ChEMBL records"*). Cut trivia a visitor can't weigh
  (*"replays 3,552 of 3,553 games"*) and findings that read as weak out
  of context (*"falls to a median 76% of cost"*).
- **Posts: short and snappy.** What the post is about, in plain words
  (*"Building a rating system for board games."*). No list of sections,
  no colon-chained subclauses.
- Implementation detail, caveats and methodology belong in the post or
  the project's own page, not the one-liner.

## Rules that keep this site from sloppifying

Hard-learned; each one exists because we hit the failure it prevents.

1. **No delta-magnitude stats.** Early games carry huge rating swings
   (high sigma), so any "biggest elo change" metric permanently crowns
   the first sessions. Records must be counts, rates, streaks, or
   durations. If a proposed stat would be won by the first game night,
   it's broken.
2. **Small-sample guards.** Every rate stat declares a minimum-sample
   floor as a named constant (`DOMINANCE_MIN_PLAYS`,
   `STUDENT_MIN_GAMES`, …) — 2-for-2 is not dominance.
3. **The session date drives everything.** Every dashboard section
   derives from `events` filtered to `date ≤ selected` via an `…AsOf`
   function. No career-only stats that ignore the picker.
4. **Dimensions are flexible.** Relative units only; wide content
   scrolls inside `.elo-tablewrap` / its own `overflow-x: auto` wrapper —
   the page never scrolls horizontally. Both themes come free via the
   CSS variables in `app/styles/tokens.css`; never hardcode a color.
5. **Delete, don't accumulate.** Cut features lose their code (grep the
   history if needed). Deliberate exceptions are shelved behind a
   comment with a note (see EloRace in `EloDashboard.jsx`) — that's the
   only sanctioned dead code.
6. **Data quirks live in `tests/data-invariants.test.js`.** Known ones:
   scores may be null (rank-only games); a play can have zero official
   winners (full tie) or several (BG Stats flags on a broken tie). Any
   derivation touching `won`/`rank`/`score` must tolerate all three.

## Testing guidelines (human and AI contributors)

- **Every derivation function gets fixture tests** with *hand-computed*
  expectations. If a test derives its expected value by re-running the
  production algorithm, it tests nothing — work the numbers out in the
  fixture comment (see `tests/insights.test.js`).
- Fixtures must be **valid payloads**: chronological events, series =
  `[0, 1000]` anchor + cumulative deltas (use the `buildPayload` helper).
- Test the **guards and boundaries**, not just the happy path: minimum
  floors produce *absent* rows, thresholds at the exact boundary
  (gap = 100 counts, 99 doesn't), the as-of date excludes later events.
- `tests/data-invariants.test.js` runs against the real `data/elo.json`
  and must pass after every data sync. When it fails on a refresh,
  first suspect the export contract changed — fix the pipeline or
  consciously extend the invariant with a dated comment; never loosen
  an assertion just to go green.
- No snapshot tests. A snapshot asserts "whatever it did yesterday,"
  which is exactly how slop calcifies.
- Before committing: `npm test && npm run build`. CI enforces both, but
  don't make CI find out first.
